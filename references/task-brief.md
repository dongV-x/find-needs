# 场景任务单

场景任务单由系统负责人或开发 Agent 准备，业务人员只需复制整段开场消息并调用 Skill，不需要自己组织背景。

## 编写原则

- 一次只研究一段能说清起点和终点的工作，不用页面名或专业词当场景名；
- 用一句人话说明目的，例如“发现一个达人后，避免团队重复联系，并知道现在由谁跟到哪一步”；
- 当前系统、已有规则和等待验证必须分开，不能把猜测写成答案；
- 只列直接相关页面，明确本次不讨论的相邻场景；
- 背景只帮助 Agent 少问废话，不应在第一问全部念给业务人员；
- 要求真实案例和资料时说明可脱敏，不强迫业务人员交出不必要的隐私数据。

## 任务单内容

```markdown
# 场景任务单

- 场景名称：
- 这次只想走通：
- 使用人/岗位：
- 系统地址：
- 对应系统版本或日期：
- 重点页面：
- 从哪里开始：
- 到什么结果结束：

## 已经确认的背景
- 只写有来源、适用范围明确的事实。

## 当前系统怎样做
- 只描述现在能看到和操作到的内容，不代表已经正确。

## 这次需要验证
- 流程是否符合真实工作：
- 实际需要记录哪些信息，旧表格中的哪些内容要保留或改名：
- 当前各阶段/状态分别代表什么，什么时候进入下一步，异常和结束怎么处理：
- 不同岗位谁能看到、谁能修改、交接时怎么处理（如适用）：
- 页面或操作是否缺失、难找、难懂或需要重复填写：
- 可能遗漏的新需求：

## 这次不讨论
- 列出相邻但暂不进入的场景。

## 已提供材料
- 文件、截图、飞书链接及其用途。

## 上一轮交接
- 首次调研填“无”；补问或复看时提供 `需求交接.md`。

## 交付位置与资料授权
- 希望输出到：
- 是否允许复制本轮明确提供的脱敏资料：是 / 否
```

任务单有缺项时，Agent 应先从链接、页面和材料中补全。只有缺失内容会明显改变调研范围或资料处理权限时，才向发起人问一个问题；不要把整张表退给业务人员填写。

## 系列调研（多场景分批推进）

整套系统按业务流程拆成多个场景分批调研时，由系统负责人维护一份**总跟进文档**（各场景的顺序、状态、任务单和交接文件位置），每场的任务单从总文档派生；上一场“待回看”里属于其他场景的条目，归档进总文档并分派到对应场景，避免丢失。Skill 本身仍然一次只处理一个场景。

## 可直接转发的开场

```text
请使用 $find-needs。
（如果你的助手没有安装这个 Skill：请先完整阅读并遵循
https://github.com/dongV-x/find-needs/blob/main/SKILL.md
以及仓库 references/ 目录下的三份参考文件，再继续。）

下面是这次的场景任务单。请先读取任务单、指定系统页面和已有材料，但不要把当前系统当成正确答案。你面对的是熟悉日常工作、但不熟悉产品术语和 AI 沟通的业务同事，请始终用大白话，一次只问一个容易回答的问题。

先从对方最近一次真实经历开始，再让他对照指定页面操作；同时完成两件事：验证当前系统是否符合实际，以及发现这段工作里遗漏的需求。跑到别的场景时先记录，继续当前主线。

结束时请生成 `需求交接.md`。获得明确授权后，才把本轮提供的脱敏资料放入附件目录；飞书链接要写进文档并标注是否实际读取。信息不足时如实输出部分交接，不要编完整需求。

[在这里粘贴场景任务单]
```

## 示例：发现达人到开始跟进

```markdown
- 场景名称：发现达人到开始跟进
- 这次只想走通：发现一个达人以后，团队怎样避免重复联系、确定由谁负责，并记录目前聊到哪一步。
- 使用人/岗位：红人营销推广同事
- 系统地址：https://实际部署地址/
- 重点页面：达人库、开发看板，以及从这两个页面打开的达人详情和新增达人窗口
- 从哪里开始：同事刚发现一位可能合作的达人
- 到什么结果结束：团队知道是否已经有人联系、接下来由谁负责、目前进行到哪里

## 当前系统怎样做
- 达人库可以搜索、新增、查看归属和达人资料。
- 开发看板可以查看和更新联系进度。

## 这次需要验证
- 同事实际会用哪些信息判断是否重复；
- 原有达人表格里哪些信息仍然需要；
- 确定负责人和更新联系进度是否符合平时习惯；
- 当前页面是否让真实工作中某一步做不下去。

## 这次不讨论
- 确定合作以后的合同、寄样、回片、付款和数据统计。
```
