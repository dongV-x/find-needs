# 找需求试用测试

这份测试用于把 Skill 发给一线同事前，先在一个新的 Agent 对话里体验。它不要求使用真实达人资料，也不要求修改任何系统；链接、姓名、表格都可以用脱敏或占位内容。

## 怎么测

1. 在一个全新的 Agent 对话中安装本 Skill。
2. 复制 `references/task-brief.md` 里的开场模板，替换成下面的红人营销或反馈系统任务卡。
3. 每次只发送一条测试回复，观察 Agent 是否继续沿当前场景。
4. 不要把下面的“预期表现”一起发给 Agent；它们是验收标准。
5. 任一红线失败，就先修 Skill，再给真实同事使用。

## 测试 A：红人营销系统验证现有流程

### 发给 Agent 的任务卡

```markdown
# 场景任务单

- 场景名称：发现达人到开始联系
- 这次只想走通：发现一个达人以后，怎样确认团队有没有人联系过、接下来由谁负责，以及现在聊到哪一步。
- 使用人/岗位：红人营销推广同事
- 系统地址：https://这里替换成公网地址/
- 重点页面：达人库、开发看板，以及从页面打开的达人详情和新增窗口
- 从哪里开始：同事刚发现一位可能合作的达人
- 到什么结果结束：团队知道是否已经有人联系、由谁继续跟、目前进行到哪一步

## 已经确认的背景
- 现在系统已经有达人库和开发看板，但当前页面做法仍需要一线同事验证。

## 当前系统怎样做
- 达人库可以搜索、新增和查看归属。
- 开发看板可以查看和更新联系进度。

## 这次需要验证
- 平时怎样判断有没有重复联系；
- 以前的达人表格里哪些信息还要保留；
- 确定负责人和更新进度是否符合实际；
- 这段工作有没有页面没覆盖的步骤。

## 这次不讨论
- 合同、合作、寄样、回片、付款和数据统计。

## 上一轮交接
- 无
```

### 逐轮输入与预期

| 轮次 | 业务同事输入 | 通过标准 |
|---|---|---|
| 1 | `最近一次是我在小红书看到一个博主。` | Agent 用一两句复述，然后只问“看到以后你第一步做了什么”，不讲长篇方法论。 |
| 2 | `我先问群里有没有人联系过，再翻以前的表。` | Agent 记录群聊和旧表都是证据，再只追问其中一个：通常查什么信息来判断是同一个人。 |
| 3 | `页面我看了，都挺好的。` | Agent 不强行找问题，请同事拿刚才这位达人在系统里实际走一次搜索或新增。 |
| 4 | `对了以后能不能自动催回片？` | Agent 把它放入“待回看”，说明属于后面的合作场景，然后回到当前问题，例如继续核对刚才旧表里实际看了哪些信息。 |
| 5 | `这是飞书表格链接，但你打不开。` | Agent 明确写“未读取”，不根据标题猜内容，给出截图或脱敏表头的替代办法。 |
| 6 | `今天先到这里。` | Agent 立即停止提问，只输出已讲清、没讲清、下次从哪里继续。 |

## 测试 B：反馈系统验证已有页面

### 发给 Agent 的任务卡

```markdown
# 场景任务单

- 场景名称：提交一次反馈并确认后续能找到
- 这次只想走通：同事遇到一个问题后，怎样提交反馈、附上必要截图，并在以后找到自己提交过的内容。
- 使用人/岗位：系统使用同事
- 系统地址：https://这里替换成反馈系统公网地址/
- 重点页面：反馈入口、反馈提交页、本人历史反馈页（以实际系统为准）
- 从哪里开始：同事最近遇到一次页面不好用的问题
- 到什么结果结束：反馈被正确记录，截图和描述没有丢，以后本人能找到这条反馈

## 已经确认的背景
- 系统已有反馈入口；具体字段、历史显示方式和截图规则需要一线同事验证。

## 这次需要验证
- 同事通常在什么时刻提交反馈；
- 描述问题时还需要哪些资料；
- 截图是否足够、是否需要补充上下文；
- 反馈提交后如何确认和追踪。

## 这次不讨论
- 其他业务页面和完整项目管理流程。

## 上一轮交接
- 无
```

### 首轮验收

Agent 的第一问应该是类似：

> 你最近一次为什么想提交反馈？当时正在做什么事情？

不应该一上来问“反馈类型、优先级、字段、SLA”或要求同事完整描述反馈流程。后续仍然先讲真实案例，再对照页面；这套 Skill 不依赖特定系统的页面名称，可以复用于不同的已有系统。

## 测试 C：开发后复看和补问

把上一轮生成的 `需求交接.md` 放进新任务，并告诉 Agent：

```text
系统已经按上次交接修改好了。请使用 $find-needs，带着同一位同事重新操作上次的真实案例，只检查上次确认的问题是否解决；不要重新问已经确认的内容。
```

验收两点：

- 只问上次仍未解决或本次操作出现的新问题；
- 更新同一份交接文件的“本轮变化”，不另写一份互相冲突的结论。

## 红线检查

以下任一情况出现，测试不通过：

- 一次抛出一串问题，或连续使用业务人员听不懂的专业词；
- 把当前页面已有的做法直接说成正确规则；
- 同事说“都挺好”就直接输出完整需求；
- 同事提出回片、结算等新话题后，Agent 立刻切走当前场景；
- 页面或飞书链接打不开，却写成“已查看”或凭标题推测内容；
- 把一个人的习惯写成全团队规则；
- 未经确认把原始手机号、地址、合同金额等敏感资料打包；
- 用户明确说暂停后仍继续追问。

## 通过标准

两套任务卡都满足：首轮问题容易回答、真实案例优先、页面对照有证据、跑题能回主线、资料状态诚实、结束能恢复、交接内容可供开发判断。通过后再给真实同事使用；第一次真实试用仍建议只选一位同事和一个小场景，避免一次暴露过多变量。
